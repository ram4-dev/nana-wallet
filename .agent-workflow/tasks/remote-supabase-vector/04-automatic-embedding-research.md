### Official capability boundaries

Supabase's automatic-embedding example combines triggers, a queue, scheduled retries and Edge inference. Its visibility-timeout mechanism supports retry after worker failure; it is an example to adapt rather than a built-in property of vector columns. [Automatic embeddings](https://supabase.com/docs/guides/ai/automatic-embeddings).

OpenAI documents multilingual embedding support and configurable output dimensions. Request `text-embedding-3-small`, `dimensions: 384`, `encoding_format: "float"`; its default is 1536, so the dimensions field is required. Spanish quality for Nana's contact corpus remains an empirical gate. [Embedding guide](https://developers.openai.com/api/docs/guides/embeddings). The API rejects empty/over-limit input and returns model, vector indices and usage; validate the response rather than accepting arbitrary JSON. [Create embeddings](https://developers.openai.com/api/reference/resources/embeddings/methods/create). The model page currently lists the model alias without a separate dated snapshot; an application revision cannot promise immutable provider weights. [Model reference](https://developers.openai.com/api/docs/models/text-embedding-3-small).

Supabase explicitly describes native gte-small as English-only. It is unsuitable for this Spanish requirement. [Running AI models](https://supabase.com/docs/guides/functions/ai-models).

## Approaches

1. Keep synchronous backend inference, or replace its model with an Edge HTTP call. Lowest queue complexity, but neither satisfies automatic SQL insertion. The latter also adds network I/O inside policy mutation transactions. Reject.
2. Copy the Supabase pgmq/pg_net/pg_cron recipe. Durable jobs and managed scheduling, but adds extension coupling absent from the compose PG16/pgvector CI environment. It still needs Nana-specific stale-work guards, failed-job handling, tenant rules and search changes. Medium-to-high effort.
3. Portable SQL transactional outbox, Edge drain worker, remote-only scheduler adapter. Adds a small queue state machine, but core migrations and concurrency tests run on existing PG16 without pgmq/pg_net. SQL writes automatically enqueue both entity types, including direct SQL. Recommend this approach. Medium-to-high effort; it is more than a small provider swap.

## Recommendation

### Transaction boundary and source of truth

Use ordinary SQL triggers on both recipients and user_memories. Each committed insert or embedding-relevant update atomically creates a durable job. The trigger never performs HTTP, inference, recipient-policy mutation, lease acquisition, or transfer work. A rolled-back wallet mutation rolls back its embedding job too. An unavailable embedding provider does not undo a confirmed contact/fact save; failure to persist the transactional outbox does abort the save, avoiding lost indexing work.

Keep contact projection writes, policy desired revision, sync intent, immutable proposal consumption, audit, expectedVersion CAS and existing wallet leases in their current transaction and service route. Delete inference from the contact mutation adapter rather than bypassing that adapter or calling a second contact writer. Existing confirmed-memory writes retain their explicit confirmation boundary. A privileged SQL insert remains a privileged administrative write; adding an embedding trigger does not grant new wallet or payment authority.

### Schema and job lifecycle

Add a new mirrored migration; do not edit historical migrations. Keep vector(384), but allow NULL for embedding and actual embedding_model_revision. Add an independent embedding_generation bigint, desired_embedding_revision, and embedding_state constrained to pending/ready/failed/inactive on both source tables. Use the same target revision literal across source defaults, worker and query client. Types that represent actual stored model revision must now accept NULL. Ready requires a non-NULL, nonzero vector and matching actual/desired revision; pending/failed/inactive must not expose a selectable semantic vector. Do not use zero vectors to satisfy NOT NULL.

Create a private embedding_jobs table with entity_kind allowlisted to recipients/user_memories, row_id, user_id, source_generation, target_revision, status, attempts, available_at, lease_token, lease_until, safe error_code and timestamps. Unique identity is (entity_kind, row_id, source_generation, target_revision). Store references rather than contact addresses, raw text or provenance snapshots in the queue. Queue retention and aggregate error monitoring are part of delivery.

On INSERT, the trigger initializes pending metadata, clears any supplied old vector and enqueues the target revision. On changes to recipient name/description, fact text, active state or desired revision, increment embedding_generation, clear vector/actual revision, and enqueue only if active. An inactive transition fences in-flight work even when business version did not change. Reactivation enqueues a fresh generation. Address/network/provenance/kind-only edits need no new inference because these fields are excluded from the embedding input. Owner and primary-key changes should be rejected or separately designed; the current application has no owner-transfer requirement. Physical deletion must leave jobs discardable and must never recreate a source row.

Trigger comparisons use `IS DISTINCT FROM` on raw source fields, not SQL approximations to JavaScript Unicode normalization. This may regenerate on a whitespace-only edit; correctness is preferable to a second normalization implementation in PL/pgSQL. Keep the existing stored normalized_name contract. Direct SQL still supplies required business fields and confirmation timestamps; embedding automation does not synthesize those.

Embedding completion updates only embedding metadata and vector. It does not change business version, recipient_versions, business updated_at, address, network, provenance, confirmation timestamps, policy state, grants or proposal status. Trigger conditions must exclude worker-only updates so completion cannot enqueue itself.

### Claim, infer, complete

1. A bounded authenticated Edge invocation claims eligible jobs using `FOR UPDATE SKIP LOCKED`, assigns random fencing tokens, advances attempts and commits the claim. Expired leases become reclaimable. Terminal/obsolete jobs cannot hold up later jobs.
2. Claim returns current allowlisted text fields only when source owner, generation, active status and desired model match the job. It returns no recipient address. A concurrent update may still happen after this read; completion fencing handles it. No transaction stays open during the provider request.
3. Edge constructs canonical input, calls OpenAI, checks model/index/count, exactly 384 finite values and positive norm, then explicitly L2-normalizes in the one provider helper. Reject malformed/zero output. Repeated inference after a crash may incur another bill; only the database effect is idempotent.
4. A narrow completion RPC locks the source row first, then the job row. Recheck source owner, entity kind, generation, active state, desired revision and the job's unexpired lease/token. Only then write vector + actual revision + ready and acknowledge the job atomically. Zero matching rows means obsolete work; do not overwrite a newer generation or mark it failed. Failure/retry updates are also fenced by job identity and token and may change source state only if it still matches.
5. Use source-before-job order for completion, invalidation and cleanup. Trigger execution already starts with the source row locked; a worker holding a job lock while acquiring its source lock would introduce a deadlock cycle. Claim transactions lock jobs only and do not take source locks. Test this explicitly with two connections.

Suggested initial drain limits, subject to design approval: one globally leased drain run, at most four jobs per invocation, provider concurrency two, 15-second request timeout, 45-second invocation budget, 90-second run/job leases, and one scheduled wake per minute. Lease tokens fence expired runs; late results are discarded. Do not build recursive function calls or rely on process-local flags to bound concurrent invocations. Tune queue and query budgets together before enabling production traffic.

### Model and text contract

Use a full application identity such as `openai:text-embedding-3-small:384:nana-text-v1:l2:epoch1`, not merely dimension equality. Record the returned provider model separately in job diagnostics if needed. Backend validates the response identity and passes the expected revision into search SQL; worker completion cannot choose an arbitrary revision. A future preprocessing/model migration advances the revision/epoch and reindexes both tables.

Keep canonical preprocessing in a small pure module within supabase/functions/_shared; backend may import that backend-only module or deliberately duplicate it with parity tests. It must not import Node transformer code into Edge or any backend module into the frontend. Preserve NFKC, collapsed whitespace, Spanish lowercase, accent preservation in embedding text, and full-string normalization after name/description or fact formatting. Retain separate accent folding for name comparison. Golden parity cases need Sofía/Sofia, Muñoz/Munoz, composed/decomposed accents, tabs/newlines and empty descriptions.

Current redaction only detects EVM literals; it does not remove Solana base58 addresses or every SNS name a user might put into a note. Never send the dedicated address column, wallet fields or provenance to OpenAI. Before approval, decide whether natural-language fields also need expanded address redaction or an explicit external-processing policy. Any redaction change belongs in the text revision and its tests. Do not claim the existing regex guarantees absence of sensitive text.

Query embeddings remain on demand: backend/voice memory runtime calls a separate authenticated Edge query endpoint using the same canonical preprocessing, provider helper, dimensions, model and application revision. Query mode returns a vector only, never source rows; it does not enqueue queries or accept a caller-specified model/table/URL. The OpenAI key lives only in Edge. No automatic local-model fallback is safe because MiniLM and OpenAI vector spaces are incompatible.

### Pending/error search behavior

Contact CRUD/list/read and confirmed memory-save success reflect committed business data, independently of embedding readiness. Saving must not promise immediate semantic availability. Existing HTTP contact payload can remain unchanged if this distinction is communicated through existing conversation behavior; adding visible indexing status would require coordinated backend/frontend contract changes and explicit scope approval.

Before requesting a query vector, perform an owner-scoped address-free current-name lookup across active rows, including pending/failed rows. Compare with the existing `comparisonTextKey`: one exact folded name can resolve, multiple matches require clarification. This is a dedicated lexical branch, not synthetic cosine similarity. Model failure must not disable it. Inspect all matches before limiting displayed candidates; never resolve a unique result merely because a second match fell outside top five.

For a minimal bounded implementation, fetch at most 1001 current name projections in one statement, use the existing JavaScript comparison, and return unavailable on overflow above 1000. This cap is a proposed operational limit requiring approval, not an existing product limit. If that cap is unacceptable, budget a persisted comparison-key strategy with SQL/JavaScript parity and direct-SQL maintenance instead. `lower(name)` alone is not equivalent to existing accent folding. Keep score optional for a lexical-only match or use an explicit internal match kind; never invent a cosine score for an unindexed row. Check voice/text result adapters for this type change.

After an exact-name miss, conservatively return unavailable if any active row needed by that search domain is pending/failed/incompatible. In particular, do not let a ready semantic result win while a pending row could be a competing recipient. Facts have no identity fallback: if active facts are incompletely indexed, return unavailable rather than empty successful evidence. A truly empty fact table may still return an empty success. This conservative per-user gate avoids introducing product-specific partial-search semantics in the first release.

When indexing is complete, semantic queries require owner + active + ready + non-NULL embedding + actual revision = desired revision = requested revision. Apply those guards to BOTH tables; default NULL ordering is not a substitute. Preserve current prefix/description/qualified-name rules and relationship-evidence checks when the candidate set is complete. Preserve the current supported-network policy and address validation; do not widen network matching under this feature.

Use a query latency budget, initially three seconds with no unbounded retry; if unavailable, report temporary retrieval unavailability and request an exact saved name. Do not report that a saved person does not exist. Exact-name success still produces only recipient id/version; the existing versioned address lookup, preview, explicit confirmation, idempotency and ambiguous-payment handling remain mandatory.

Revalidate thresholds and bonuses with Spanish and English cases before allowing semantic selection. If the new model has not passed acceptance, keep semantic selection disabled or clarification-only; do not mechanically reuse 0.78/0.55/0.08. Test relationships, close semantic neighbors and duplicate names, not just self-distance or a successful 384-dimensional response.

### Retries, rate control and security

Classify network timeouts/5xx/429 as retryable; honor Retry-After with bounded exponential backoff and jitter. Start with five per-generation attempts, then terminal failed state and an operator-visible error code. Invalid input/too-long text is poison work: isolate it without blocking the queue, and allow a changed source generation to start fresh. Authentication/quota/configuration failures should pause/circuit-break the drain and alert, rather than exhausting every row's retry budget. An operator retry must be explicit, bounded, and cannot alter source confirmation or wallet state.

Current name/description/fact/query schemas lack embedding-sized maximums. Enforce function request byte limits and a conservative canonical text byte cap before inference (proposed 6000 UTF-8 bytes); never silently truncate identity text. Oversized source rows may remain saved but fail indexing honestly; oversized queries return unavailable/validation failure. A conservative byte ceiling avoids adding a tokenizer just for short contact text. Finalize this limit and messaging in design.

Use separate function-scoped random credentials for drain and query, checked by their handlers before body parsing or any provider/database work. These custom credentials require explicit per-function `verify_jwt = false` plus mandatory handler authentication; Privy identity tokens are not Supabase session JWTs. Separate endpoints prevent a query credential from claiming jobs. If using Supabase native secret-key auth instead, use its documented `apikey`/secret mode, never publishable auth or merely turning off JWT verification. [Function authentication](https://supabase.com/docs/guides/functions/auth).

Keep queue tables outside exposed API schemas, with no public/anon/authenticated/recipient_app direct access. Trigger definer functions only derive owner/id from NEW; they accept no user-supplied SQL/table names. Completion/claim RPCs in an exposed schema must revoke default PUBLIC execution and any direct client grants; grant only to the privileged worker role (service_role remotely, a deliberately provisioned test role locally). Pin search_path and fully qualify names, including vector operators/casts. Owner-bound source checks remain necessary even inside privileged RPCs. [Database function security](https://supabase.com/docs/guides/database/functions).

The Edge admin database credential stays inside Edge and serves only the audited RPC surface. Do not forward it to backend or frontend. Source metadata/vector writes should be reserved to worker RPCs; revise broad recipient_app table grants into business-column grants without disturbing existing policy writes. Explicitly test forced RLS and definer privileges on hosted Supabase as well as PG16. Do not rely on PostgREST's user JWT propagation for Nana's app.user_id policies.

Bound query requests per authenticated user in backend, and bound total provider requests/tokens across query and drain traffic with a shared budget/circuit breaker rather than per-isolate memory. Reserve query capacity so backlog cannot starve live voice. Record counts, ages, attempts, latency and sanitized codes; never log raw text, vectors, authorization headers, provider bodies or secret values. Provider account rate limits and spend controls require deployment-specific verification, not assumed documentation defaults.

Supabase scheduling can invoke an Edge function via pg_cron + pg_net and obtain an auth token from Vault. The current documentation warns that database logins can read the decrypted key while it waits in net.http_request_queue. [Scheduling functions](https://supabase.com/docs/guides/functions/schedule-functions). Therefore send only a drain-scoped credential, never the project admin key or OpenAI key. Prefer a backend/external scheduler with that narrow credential if the SQL-login exposure is unacceptable. Record that tradeoff before enabling pg_net. No scheduling tool or recurring agent is being created by this research.

Keep scheduling separate from portable schema migration: a tracked remote setup script can enable extensions, provision its credential reference and register one named cron job after explicit deployment approval. Core migrations contain no pg_net/pg_cron/pgmq requirement and no secret. CI invokes the drain directly against disposable infrastructure. An external scheduler is an equivalent wake adapter; SQL writes still trigger durable generation automatically after commit.

An ordinary code rollback to old readers is unsafe once new vectors exist. ## Checks and acceptance evidence

## Risks and unresolved product decisions

The new user direction selects automatic generation, but does not settle these design choices:

1. Accept OpenAI processing of contact names/descriptions/facts/queries, its cost and operational budget; resolve Solana/SNS text redaction and privacy requirements before any real data is sent.
2. Accept eventual semantic availability, a proposed one-minute wake cadence, exact-name lookup during outage, and conservative per-user semantic unavailability while any relevant row is pending/failed. Decide whether UI needs visible indexing status; baseline preserves the HTTP contact payload.

4. Decide whether the documented pg_net credential exposure is acceptable for a drain-only token; otherwise choose an external/backend scheduler. Accept a controlled writer pause for cutover, or explicitly request a larger side-by-side migration if zero downtime is required.
