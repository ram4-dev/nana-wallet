# Design: slice3-grant-execution

Binding: spec (61 scenarios), proposal (Q1–Q4, D-2/3/4/7), exploration §2/§3/§6/§7. Line refs spot-verified.

## Context

Grant engine unwired (`DelegatedGrantService` at `src/server.ts:191`, grant routes only). All confirmation sites funnel through `resolveDecision` (`src/conversations/service.ts:430`) → attempt claim (`:508`) → `runFinancialTransfer` (`:730`, honest `uncertain` wording `:823-841`). Exploration §7 names the seam.

## Architecture Decisions

**AD-1 Single seam, optional deps.** Optional grant deps on `WalletConversationDependencies`, wired from `server.ts:191`; absent ⇒ today's behavior byte-for-byte. *Rejected:* per-entry-point wiring (divergent text/voice).

**AD-2 Two-phase authority; two moments.** Pre-filter = static bounds only (lifecycle, expiry, per-transfer cap on converted units, allowlist, action/chain, wallet match, units integrity) — **no consumption read anywhere in the conversation path (structural invariant)**. It binds **explicit intent** first: exact amount + resolved recipient traceable to the authenticated original user turn/transcript via existing parsing/resolution; ambiguous/absent/unmatchable ⇒ degrade; tool arguments never backfill. `claimConsumption` (`consumption.ts:382-512`) is the sole execution authority: user-scoped tx + advisory lock re-checks state, DB-clock expiry, policy binding, caps, rolling window; claim + `used` audit commit together before broadcast. Request-time classification enforces Q1 (grant `created_at` after the original request turn ⇒ not a candidate); claim recheck guards TOCTOU. *Rejected:* `evaluateGrant` as authority; `consumedInWindow` with a raw client (returns 0).

**AD-3 Eligibility (model-tool exclusion).** Skip only when the shared service processes the authenticated original user turn/transcript (typed `handleTurn`; voice transcript `src/livekit/room-conversation.ts:195-217`). Model-produced tool previews (`send_token`/`previewTransfer`: `create-realtime-tools.ts:265-285`, `src/agent/livekit-adapter.ts:109-116`) stay preview + explicit-confirm — auto-skip would be model-delegable (violates D-3). Mechanism: server-decided preview-origin marker (user request vs model tool) on `previewTransfer`; classifier consults the marker, never tool payload; plus AD-2 intent binding. Non-covered previews unchanged. Slice 4 keeps voice-confirmation UX. *Rejected:* eligibility from tool arguments.

**AD-4 Selection (Q3).** Order: per-transfer cap ↑ → cumulative cap ↑ → earliest expiry → stable grant id. Iterate all static-eligible candidates; any claim rejection ⇒ next candidate; degrade when exhausted. Wrong `wallet_id` ⇒ never a candidate. No model/client parameter exists. *Rejected:* single top-ranked attempt (strands payable requests).

**AD-5 Units.** Decimals from provider `listTokens(network)` (`provider.ts:13,66-67`; SOL = 9, `solana-devnet-provider.ts:322`). Human decimal string → integer smallest units via string/`BigInt` math only; unknown token / missing decimals / non-integral ⇒ degrade closed. No clamping; ceiling acts via ordinary coverage comparison. *Rejected:* hardcoded decimal tables.

**AD-6 Idempotency: two independent single-winner gates; claims are RESERVATIONS until dispatch certainty.** Key `grant-exec:{userId}:{attemptId}` from the persisted `conversation_transfer_attempts.id`; `grant_claim_ledger` unique key + replay branch (`consumption.ts:395-409`) enforce budget idempotency. A `claimConsumption` replay returns the same budget claim with no second consumption/audit — it NEVER implies a completed transfer. Any broadcast must also win the single-winner `claimPendingTransfer` transition (`previewed → broadcasting`, `postgres-repository.ts:364-395`); a `broadcasting`/terminal attempt cannot broadcast twice. Crash after budget claim but before attempt claim ⇒ same-key retry is safe and proceeds only if the attempt transition is won — retries are never stranded by a blanket "replay ⇒ no broadcast". A persisted claim row is a reservation (see AD-10): it is charged against the window until released, and release is possible only on definitive non-dispatch. *Rejected:* session-counter keys; parallel idempotency table.

**AD-7 Covered flow, narration, contract.** Covered ⇒ skip confirmation branch, reuse the same `runFinancialTransfer` boundary (re-validation untouched). Honest narration; `uncertain` wording verbatim; no cancel window. Result = existing `sent` shape (`http.ts:119`) ⇒ **zero contract delta**; mirror = no-op assertion that both contract files agree; unforeseen delta ships mirrored same PR. Never use the stale client `confirmTransfer` route. *Rejected:* new `auto_executed` variant.

**AD-8 Closed degradation (Q4).** Every non-covered outcome (conversion failure, no candidate, claims rejected, engine/ledger/DB/unknown errors, ineligibility) ⇒ copy "the active authorization did not cover this request" + standard preview/confirm flow. Reason codes internal; no budget consumed; no `used` row (rejected-claim audit rows allowed); never a hard error.

**AD-9 Policy readiness & drift.** Ledger binding check gates (`policy_not_ready`); broadcast relies on Privy enclave enforcement. No new execution-time readback. Ledger-vs-Privy drift at execution = accepted risk.

**AD-10 Reservation release (binding user decision).** Budget claims are reservations until dispatch certainty. Release REASONS, each executed SOLELY by the atomic owned-CAS settlement authority defined in (2) — never as independent release paths:

1. **Definitive `not_dispatched`** (`service.ts:985` branch): a settlement reason `not_dispatched`; this branch already proves no transaction was sent. Executed only inside the (2) settlement transaction.
2. **Owned-broadcasting CAS is the ONLY release authority**: settlements originate in `runFinancialTransfer`, which enters with the attempt ALREADY `broadcasting` under the winner's persisted `claim_id` (claim won first, then policy/recipient validation, then `broadcastTransfer`) — so BOTH preflight rejections and definitive `not_dispatched` settle from the owned `broadcasting` state via the compare-and-set `broadcasting → cancelled` on the EXACT row (id + status + `claim_id` all match). Losing the single-winner `claimPendingTransfer` transition, a stale `claim_id`, a moved status, an absent row, an already-`cancelled` status, or ambiguous ownership NEVER release standalone — they RETAIN the reservation (a loser's claim is a live-claim replay; the winner may be broadcasting under the same reservation). No `previewed → cancelled` release path exists for these settles; every retained dispatched/uncertain state — `broadcasting` (unowned), `submitted`, `uncertain`, `confirmed`, `reverted`, `receipt_invalid` (migration 002 CHECK) — keeps the reservation.
3. **Pre-broadcast rejection**: policy or recipient rejection after the claim but before any dispatch ⇒ a settlement reason carried by the same (2) atomic CAS settlement — no independent release path.
Retain (never release): `submitted`, `uncertain` (including the provider-exception mapping at `service.ts:972-978` — the request may have left the process), any in-flight `broadcasting` attempt, and any attempt whose winner ownership cannot be distinguished from an in-flight dispatch (concurrent-winner rule above); recovery for retained budget is existing reference-id reconciliation.
Mechanism: the settlement of execution opens ONE `withUserTransaction` (with the per-grant advisory lock `dgc-grant-{id}` acquired inside it) and passes its transaction client to a TX-ONLY ledger method `releaseReservationInTransaction(tx, {grantId, userId, idempotencyKey, reason})` — the method does NOT open, commit, or nest any transaction of its own: attempt CAS, ledger update, and `released` audit all run on THAT SAME client so the database guarantees atomicity (no application-level pseudo-transaction). An already-released row is returned unchanged (no second audit row, no timestamp/reason overwrite); replayed live claims are NOT released (a replay returning `replay: true` never authorizes release — release requires a settled definitive non-dispatch for THIS execution); attempt-state-keyed release MUST consult current persisted attempt state/ownership before releasing, never the mere failure of the attempt transition. If a standalone transaction-opening release API is ever added for other operations, it sits OUTSIDE the settlement authority and MUST NOT release a grant execution claim without the owned-CAS proof. **Atomic settlement with ownership token (final review blockers):** ONE atomic user-scoped transaction performs the attempt compare-and-set + ledger release + compensating `released` audit under the per-grant advisory lock — any part failing rolls back ALL of it. The `claimPendingTransfer` winner result RETURNS the persisted `claim_id` token (already persisted by migration 002; result shape changed) and `runFinancialTransfer` threads it to settle: BOTH preflight rejection and definitive `not_dispatched` CAS the exact attempt row `broadcasting → cancelled` WHERE id, status, AND `claim_id` match, then release the exact grant/idempotency claim and insert the audit row in the SAME transaction; a lost/absent CAS releases NOTHING and retains. The existing broadcasting-to-previewed reset (`releasePendingTransferClaim`) is REPLACED — a released attempt is never re-opened; ambiguous/absent ownership ⇒ retain. **No re-activation (binding user decision):** same-key re-activation was REJECTED — it creates lifecycle races (an old settle could release a live retry) requiring cross-transaction generation/ownership coupling. The claim_id CAS above is the coupling-free ownership proof. A released key is permanently retired: the `claimConsumption` replay branch MUST fail closed for a released key (never `consumed`, never authorizing a broadcast); a retry creates a FRESH persisted `previewId` — fresh key, fresh reservation, full grant/window/cap checks. Provider reference identity stays verbatim-stable ONLY for retained outcomes (`submitted`/`uncertain` retries reconcile by reference). **Window accounting (explicit query rewrite, not additive):** BOTH existing window sums read `grant_audit_log` `used` rows — the claim's authoritative total (`consumption.ts:462`) and the engine prefilter `consumedInWindow` (`consumption.ts:168`) — so adding columns to `grant_claim_ledger` alone cannot free budget; BOTH queries are rewritten to sum UNRELEASED `grant_claim_ledger` rows (`released_at IS NULL`, claimed inside the window). Migration `012_grant_claim_release.sql` (+ Supabase `20260901001100`): additive `released_at TIMESTAMPTZ`, `released_reason TEXT`, `released` added to the `grant_audit_log` event CHECK, `UPDATE` grant on the claim table to `recipient_app` — all under the existing forced-RLS `user_isolation` policy (no policy change; release runs inside the user-scoped transaction with `app.user_id` set). *Rejected:* releasing on `uncertain` (budget could be double-spent); scheduled sweeper as release authority (release is settled-outcome-driven only); new idempotency table; same-key re-activation with a version/generation token (lifecycle races; the fresh-preview contract above needs no cross-transaction generation coupling); stateless release without the claim_id CAS (an old settle could release another worker's live dispatch).

**AD-11 Persisted preview identity guard (HIGH PR #3 remediation).** `SolanaDevnetProvider.broadcastTransfer` SHALL fail closed on missing/empty/whitespace-only `previewId`: return `not_dispatched` BEFORE `requireRecentBlockhash` and BEFORE `signAndSend` — no timestamp/random fallback reference. This restores the previously-reviewed guard (slice2 commit `e39dbad`, "fail closed without Solana preview ID") that the slice3 provider rework accidentally dropped. A valid `previewId` is used verbatim as the dispatch reference, preserving retry identity for reconciliation; this identity stability applies to RETAINED outcomes (`submitted`/`uncertain`), while a definitively released key is retired and any retry uses a fresh persisted previewId (AD-10). Tests RED-first in `tests/unit/solana-devnet-provider.test.ts` (spy seams prove order: guard precedes RPC and signer). Out of scope here: budget claim/refund semantics for the resulting non-dispatch — governed by AD-10. *Rejected:* `sol-${now()}` fallback (unpersisted identity breaks reconciliation); throwing instead of `not_dispatched` (loses the honest outcome shape).

## Flow

classify (intent bound, static only) → ordered candidates → reservation claim (+ `used` committed) → skip confirmation → `claimPendingTransfer` single-winner WINS and returns the persisted `claim_id` ownership token → `runFinancialTransfer` (attempt now owned-`broadcasting`): policy/recipient preflight validation — rejection, or later provider `not_dispatched`, settles SOLELY through the ONE atomic user-scoped settlement transaction: exact-owner CAS `broadcasting → cancelled` (id + status + `claim_id` all match) + ledger release + compensating `released` audit; a lost/absent CAS, absent row, or already-`cancelled` status retains (never releases standalone) → `submitted`/`uncertain` ⇒ retain (reconcile by reference); retry of a released key fails closed — a fresh persisted previewId claims a fresh reservation → `sent` + honest narration. Degraded: not covered ⇒ copy + `confirmation_required` ⇒ existing confirm/cancel. Race: unique key + advisory lock ⇒ one winner; loser tries next candidate or degrades (a loser sharing the winner's reservation retains it, never releases); released budget re-enters the rolling window through the REWRITTEN ledger-based sums.

## Data/State

Schema: one additive migration, `012_grant_claim_release.sql` + Supabase `20260901001100_grant_claim_release.sql` — `grant_claim_ledger` gains `released_at TIMESTAMPTZ` (NULL = held reservation) and `released_reason TEXT`; `grant_audit_log` event CHECK gains `'released'`; `UPDATE` grant to `recipient_app`. No table drops, no policy changes, forced RLS unchanged. PLUS an explicit query rewrite (not additive): both window sums (`consumption.ts:462` claim total, `consumption.ts:168` `consumedInWindow`) change from `grant_audit_log` `used` rows to unreleased `grant_claim_ledger` rows. All four existing tables otherwise unchanged. New in-process only: preview-origin marker (OPEN-1: persist only if cross-process recomputation is proven), optional deps.
