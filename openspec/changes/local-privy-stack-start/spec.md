# Requirements

1. The launcher SHALL expose exactly `https://nana-privy.localhost` by default through Portless HTTPS on 443. Given an insecure/custom-port proxy, startup SHALL fail or obtain system authorization to start the required proxy; it SHALL NOT silently return an HTTP alternative.
2. The frontend SHALL use `/api`, and the API SHALL return `wss://nana-privy.localhost/livekit`. Given a real browser request to `/api/v1/live-bindings` without authentication, the API SHALL return 401 through the proxy, without CORS failure. Vite SHALL proxy WebSocket signaling and strip the `/livekit` prefix as the Docker Nginx does.
3. Credentials SHALL be injected using `vault-env`; no provisioned `.env` is read by the launcher and no values are logged. Given missing keys or a mismatched linked Supabase target, startup SHALL fail with a safe diagnostic. The Nana Landing target SHALL remain untouched.
4. The launcher SHALL start API, worker, LiveKit, and existing loopback-only signer topology. Only sidecars SHALL receive the private authorization key. Given a consumer recreation, its signer SHALL join the current network namespace. Tests SHALL remain on disposable local databases; remote startup SHALL use read-only probes only.
5. Readiness SHALL check trusted HTTPS frontend 200, same-origin API health, binding 401, WSS proxy upgrade, remote DB read, worker registration, and signer capability. Given a failed check, the command SHALL exit nonzero and not announce a ready stack.
6. Given a second invocation, only owned resources SHALL be reused/recreated, and unrelated Portless routes, containers, worktrees, and database contents SHALL remain unchanged. The documented command SHALL cover automatic dependency startup when possible and clear local authorization requirements.
