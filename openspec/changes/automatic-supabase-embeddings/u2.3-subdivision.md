## Consumption, release and lock rules

Consumption locks the drain source first, then job, then control, then reservation, and validates the complete tuple plus active pending source and current live run/claim after waits. Query start locks control then its reservation. Only RESERVED→STARTED increments job attempts, at most5; a duplicate start returns `already_started` without provider permission or increment. Refused admission, unused reservation, duplicate/stale start and pause never spend a new attempt. Finish changes only reservation occupancy. Never decrement attempts after a STARTED call, including global provider faults.

An unused drain reservation expires at min(admission+15s, job lease, run lease); STARTED sets expiry to min(start+15s, job lease, run lease). The adapter must abort at that returned bound. Query expiry is admission+3s and never extends on start; backend/Edge enforce the remaining end-to-end deadline. Transport finishes in a finally path on success/error/abort, including stale publication. A lost finish acknowledgement is harmless: retry is idempotent and bounded expiry remains. Limits describe admitted client operations; remote cancellation does not prove the provider stopped computing.

The additive `embedding_private.job_reservation_after()` trigger on jobs releases the matching reservation when completion produces `done`, terminal failure produces `failed`, or a known finished transient failure returns to `pending`. Existing SQL023 completion is not replaced. Lifecycle supersession, token rotation and pause defer release RESERVED immediately; STARTED remains counted until transport finalization or expiry because HTTP may still be outstanding. Distinguish pause codes from finished transient codes. Trigger/finish never refund minute charges, alter sources, or release a newer claim's reservation. A stale completion that changes no job is cleaned through finish/expiry. Already-persisted jobs/reservations/counters survive rollback of rollout.

Blocking lock order is source→job→control→reservation for source-aware operations, job→control→reservation for drain admission, control→owner-minute→reservation for query admission, and reservation-only for finish/transition cleanup. Trigger cleanup takes no control/source lock. Claim remains job-only with respect to sources and pins control after acquiring jobs. No path may hold control while waiting on a source/job. Control-only operations must commit before subsequent job/source work.

Pause phase1 locks only control and validates the safe code plus either the current unexpired drain run (NULL reservation argument), or an unexpired STARTED query reservation (NULL run argument). It reads query reservation validity without taking job/source locks; simultaneous finish cannot authorize another operation. It writes pause_code, expires any current drain run and commits. Query faults therefore pause globally even when no drain run exists. It leaves any existing drain token to identify cleanup; it does not loop over jobs in that transaction. Phase2 `defer_paused` takes up to4 matching-run job locks via SKIP LOCKED, pins control afterward, rechecks the paused run, clears their claim/lease and returns them to pending without resetting attempts. It never locks sources. A crash between phases is safe: control fences new work/results, reservations expire and jobs remain reclaimable/recoverable. Operator repair/unpause is explicit; no automatic retry reset.

Completion/pause linearize at control: completion holding control SHARE may finish before pause commits; completion waiting behind committed pause must return stale. Admission/start and replacement claims also revalidate paused control after waiting. This prevents introducing a lock inversion; no existing deadlock is asserted.

## Fifth-attempt recovery (C2)

SQL022's `attempts<5` claim filter cannot reclaim a fifth-start crash. Live failure cannot repair an expired claim. U2.3e therefore adds a bounded maintenance RPC, without weakening completion/failure leases. It runs while activated, including while paused/claims-disabled; it performs no inference. The later drain calls recovery in its own committed transaction before begin/claim, never nested under a control lock.

Discover exhausted candidates without job locks: attempts=5 and either leased with lease_until≤clock_timestamp() or pending. Cap at4; acquire each source then job with SKIP LOCKED, never waiting for later sources while retaining prior locks. No control lock is acquired in this multirow cleanup. Distinguish a source skipped because locked from an absent source; skipped rows have no side effect. Recheck attempts/state/expiry and exact tuple after acquisition. For the matching active pending generation, atomically mark source embedding_state failed and job failed with safe `attempts_exhausted`, clearing claim/lease. Do not alter vector identity/business timestamps/version/history/policy/grants. Changed generation/incarnation/revision, archive or deletion never changes the current source; obsolete exhausted jobs may become superseded. Live fifth attempts are untouched. Concurrency and lease expiry are checked with clock_timestamp, not transaction-start now().

Actual C2 proof in e must obtain five STARTED results through admission/start and real transient failures, withholding the fifth outcome. Recovery before expiry changes nothing; after expiry it fails only that generation. Claim/start cannot produce attempt6. A concurrent edit/delete/reinsert wins safely, stale results remain fenced, and healthy other work progresses. Operator-only expected-generation retry is then the sole reset path: under the source lock, require failed active current generation, require desired revision equals the control target and set only `desired_embedding_revision=NULL` through the existing lifecycle guard, whose distinct-value check restores target and advances generation/clears vector/enqueues without a business edit; retain the old job/counters. Prove the guard actually increments once on both tables. Do not fake a content change or toggle business status.
